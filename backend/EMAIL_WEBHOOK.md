# Provider-neutral email webhook

`GET /api/ready` reports core database readiness plus non-secret optional integration states: `optional_integrations.attachment_scanner` is `READY`, `UNAVAILABLE`, or `NOT_CONFIGURED`, and `recipient_region_routing` is `READY` or `CENTRAL_FALLBACK_ONLY`. `deployment_constraints.tenant_scope` is `SINGLE_TENANT_ENFORCED` in production until every persistent and file-backed store is tenant-isolated, and `DEVELOPMENT_MODE` otherwise. ClamAV readiness uses a bounded `PING`; it does not scan a file or prove signature-database freshness. Backend core readiness remains separate, so a missing optional scanner is visible without hiding the safe review fallback.

`POST /api/webhooks/email` accepts the raw bytes of one `.eml` or `.msg` message and passes it through the normal analysis and investigation pipeline. It does not use OAuth or connect to a mailbox provider. A mail gateway or user-owned adapter must post messages to this endpoint.

After analysis the response includes `mail_flow_decision` with `recommended_action` (`ALLOW`, `REVIEW`, or `QUARANTINE`), `delivery_action`, severity, score, confidence, rationale, and (for review/quarantine decisions) a safe `user_notification` explanation. A trusted gateway adapter must consume that response and apply the delivery action to its own mail flow. MailTrace itself does not move, hold, release, or quarantine mail. `user_notification` is structured guidance for the gateway or organization UI to show the recipient; it explains detected risk indicators and advises the user not to click links, open attachments, reply, or send credentials/money.

Enforcement responses initially report `gateway_action.status=PENDING_CONFIRMATION`; they are recommendations until the gateway confirms its result. After applying the decision, the trusted adapter can post a signed receipt to `POST /api/webhooks/email/{event_id}/action-receipt`. Configure a separate `MAILTRACE_GATEWAY_ACK_SECRET` (at least 32 characters) for these callbacks. The JSON fields are `timestamp`, `idempotency_key`, `action`, `outcome`, and optional `gateway_message_id` and `reason_code`. Sign the canonical UTF-8 JSON object containing these fields plus `event_id`, with sorted keys and compact separators, using HMAC-SHA256 and send it as `X-MailTrace-Signature: sha256=<hex>`. The signed timestamp expires after five minutes. `action` must match the stored policy recommendation; an enforced decision accepts `APPLIED` or `FAILED`, while a monitor-only decision accepts `OBSERVED` or `FAILED`. Receipts are idempotent per event/key and stored in an append-only hash chain. A failed or missing receipt must be treated as unresolved by the gateway adapter and surfaced to operations; this callback records the gateway's assertion and does not independently prove that the mail system applied the action.

Policy settings:

- `MAILTRACE_GATEWAY_ENFORCEMENT_MODE=monitor_only` is the safe default: the gateway receives a recommendation, but `delivery_action` remains `MONITOR_ONLY`.
- `MAILTRACE_GATEWAY_ENFORCEMENT_MODE=enforce` returns the policy action as `delivery_action`. The gateway adapter must hold the message while analysis runs, map `REVIEW` to the organization's review/hold flow and `QUARANTINE` to quarantine, and apply the organization's explicit fail-open/fail-closed timeout policy. Only enable this after the adapter has been built and validated end to end.
- `MAILTRACE_REVIEW_THRESHOLD=40` is the default review threshold (allowed range 0–99 and must stay below the quarantine threshold). A message at or above it, or with a suspicious/high verdict that lacks enough confidence for quarantine, is sent for review. Review results do not automatically create SOC cases; an employee can submit a report through the separate employee API below.
- `MAILTRACE_QUARANTINE_THRESHOLD=85` is the default score threshold (allowed range 50–100). Automatic quarantine and SOC alert/case creation require a high-risk score or critical verdict plus independent fusion confidence, at least 0.80 overall confidence, at least 0.70 evidence confidence, five supporting signals, and two independent evidence categories. A risk score alone never raises confidence. Lower-confidence high-risk results are held for review, not silently allowed. The mail webhook itself does not identify or authenticate employees.
- Missing, malformed, out-of-range, or unsupported threat assessment fields produce `REVIEW`; they never fall through to `ALLOW`. In enforce mode the gateway must keep the message in its review/hold flow until an authorized policy or analyst resolves it.

High-confidence auto-quarantine detections and ClamAV-confirmed malware create a durable SOC alert linked to the investigation and an automatically opened case. Analysts can read alerts via `GET /api/alerts`, acknowledge one via `POST /api/alerts/{alert_id}/acknowledge`, resolve one via `POST /api/alerts/{alert_id}/resolve`, and read the append-only alert event history via `GET /api/alerts/{alert_id}/history`. In hosted mode, investigation, case, alert, evidence, report, campaign, and threat-intelligence APIs require a SOC role (`analyst`, `soc_lead`, `tenant_admin`, or `platform_admin`) in addition to the relevant `read`/`write` permission.

Automatic alert cases route to a regional SOC queue only when the HMAC-signed SMTP context contains exactly one recipient and a tenant administrator has mapped that employee email and OIDC subject to a region with `PUT /api/soc/routing/employee-regions/{subject_id}`. The mapping body accepts `email_address` alongside `region_key`, `team_key`, `active`, and the required audit `reason`; configure `MAILTRACE_ROUTING_EMAIL_HMAC_KEY` (at least 32 characters) before saving these mappings. The database stores only a keyed HMAC of the normalized address, not the email itself. Keep the key stable; changing it requires re-saving mappings. Multiple recipients, duplicate active address mappings, missing mappings, or inactive regional queues use the Central SOC fallback. The untrusted message `To` header and IP geolocation are never used for employee region routing.

Threat-intelligence lookups during email analysis use the local feed cache; they are not live per-indicator queries. `/api/threat-intelligence/status` and each analysis result expose provider configuration, last attempt/success timestamps, error type, local indicator counts, and freshness/coverage. Sync runs are append-only and identify the analyst or scheduler that initiated them. Configured feeds refresh in the background every 60 minutes by default; set `MAILTRACE_TI_SYNC_INTERVAL_MINUTES` to 15–1440 minutes to change the interval or `0` to disable scheduled refresh. A stale, never-synced, or unavailable feed is shown as limited coverage; no-match results under limited coverage must not be treated as evidence that an indicator is benign.

Email attachments receive bounded, non-executing file-signature and extension-consistency analysis for up to 50 attachments per message. Each attachment is limited to 10 MiB and the total decoded attachment processing budget is 50 MiB per message; file-type analysis reads at most the first 64 KiB. Within those limits, attachments are SHA-256 fingerprinted without persisting a second plaintext copy. Oversized attachments or attachments beyond the cumulative byte budget are not decoded or fingerprinted and are explicitly marked unanalyzed. Static file-type metadata keeps `malware_confirmed` unknown; it never signals that a file is malware-free. Never treat a missing signature finding as proof that an attachment is clean.

Optional ClamAV scanning uses clamd's `INSTREAM` protocol without writing attachment bytes to disk. Configure `MAILTRACE_CLAMD_UNIX_SOCKET` for a local Unix socket, or set both `MAILTRACE_CLAMD_HOST` and `MAILTRACE_CLAMD_PORT` (default `3310`) for a trusted private network endpoint. The clamd TCP protocol has no encryption or authentication; never expose it to an untrusted network. `MAILTRACE_CLAMD_TIMEOUT_SECONDS` defaults to 2 seconds and is capped at 5 seconds. At most 10 attachments and 5 seconds of scan time are spent per email. Scanner results are `CLEAN`, `INFECTED`, `ERROR`, or an explicit not-scanned/unconfigured state; only a scanner-reported match sets `malware_confirmed=true`, and only a scanner-reported clean response sets it to `false`. Scan errors, limits, and missing configuration remain unknown and feed a coverage-limited signal; they are not successful scans. A ClamAV match produces a high-confidence malware-delivery signal and a quarantine recommendation. `MAILTRACE_REQUIRE_ATTACHMENT_SCAN=true` is the safe default: any message with an attachment lacking a verified clean or infected result is sent for review instead of being allowed. Set it to `false` only when another trusted gateway control owns the required attachment-scan policy. This is still not isolated detonation/sandboxing. MailTrace does not itself quarantine or release mail; the configured gateway must apply the returned action and confirm the outcome.

Attachments 51–200 retain size/hash metadata when within the byte budgets and are explicitly marked unanalyzed; after 200, further payloads are skipped and a count marker records how many were omitted.

Employee report API (interim identity mode): configure a distinct API key for each employee with roles `read`, `write`, and `employee`, plus server-side `subject_id` and `email` attributes. Employee credentials cannot be combined with SOC, admin, or service roles. `POST /api/employee/reports` accepts an `investigation_id`, one of `suspicious`, `clicked_link`, `opened_attachment`, `shared_credentials`, or `made_payment`, and an optional `employee_note` of up to 1,000 characters. The server verifies that the HMAC-signed SMTP envelope recipient list includes the configured employee email; the attacker-controlled `To` header is not used for ownership checks, and client-supplied reporter identities are not accepted. A report creates a case, repeated reports for the same employee/message deduplicate, and a later report can raise its priority. New reports are limited to 10 per employee per hour; all submissions, including duplicates, are capped at 30 per hour. Do not include passwords, OTPs, or other secrets in `employee_note`. `GET /api/employee/reports` lists only that employee's reports; `GET /api/employee/reports/{report_id}` returns only that employee's report status. Employee responses include only the report ID, incident type, priority, coarse status, and timestamps; SOC case IDs, investigation IDs, queue, assignee, region, skills, and SLA details remain investigator-only. Click/open reports are HIGH priority; credential-sharing/payment reports are CRITICAL.

SOC case claims: an analyst API credential needs its own `subject_id` to claim work. `POST /api/cases/{case_id}/claim` atomically claims a case for 20 minutes; the same analyst can renew by claiming again. Another analyst receives HTTP 409 while the claim is active. `POST /api/cases/{case_id}/release` releases only the caller's claim. Updates, evidence attachment, and case notes are rejected while another analyst holds a valid claim. Expired claims can be reclaimed, and each claim, renewal, expiry reclaim, and release is recorded in `case_claim_events`. Local loopback development uses the synthetic `local-dev-analyst` principal; hosted deployments use the configured analyst `subject_id`.

This API-key mapping is an interim, individually assigned credential model—not organization SSO. OIDC/SAML integration, revocation/rotation management, regional queue assignment, and per-user case authorization remain required before production rollout. The webhook still performs analysis and records an investigation for every submitted message.

The route is disabled unless `MAILTRACE_WEBHOOK_SECRET` is set to a secret of at least 32 characters. Each request must include:

- `X-MailTrace-Filename`: a simple filename ending in `.eml` or `.msg`.
- `X-MailTrace-Event-Id`: a stable delivery ID from the gateway, reused when retrying the same delivery.
- `X-MailTrace-Timestamp`: Unix timestamp in seconds; requests expire after five minutes.
- `X-MailTrace-Signature`: `sha256=` followed by the lowercase hex HMAC-SHA256, using the configured secret. The signed bytes are the UTF-8 JSON object `{event_id, filename, smtp_context, timestamp}` serialized with sorted keys and compact separators, followed by a newline and the exact raw body.

For trusted SMTP/SPF verification, the adapter may supply all of these headers together: `X-MailTrace-SMTP-Client-IP`, `X-MailTrace-SMTP-Mail-From`, and `X-MailTrace-SMTP-HELO`. It may additionally supply `X-MailTrace-SMTP-RCPT-TO` with the actual SMTP envelope recipient addresses. All supplied values are included in the HMAC. The secret must only be available to a trusted mail gateway; values submitted directly by an end user are not trusted SMTP context. The IP is canonicalized, HELO and recipients lowercased, and recipient addresses normalized before signature verification. SPF stays unverified unless the three SPF context headers are all present. Employee reporting is denied for investigations without the signed SMTP recipient context.

The maximum message size is 25 MiB. Webhook event IDs and delivery status are kept in SQLite for 30 days; raw messages are not duplicated in the retry ledger. Completed duplicate deliveries return the existing investigation ID. Failed deliveries can be retried by posting the same event ID, message, and SMTP context with a fresh timestamp and signature; the attempt count is recorded. A duplicate still processing returns HTTP 202. A processing entry untouched for 10 minutes is reclaimed on the next identical delivery after a worker crash.

`GET /api/threat-intelligence/stream` sends the dashboard an initial snapshot and then server-sent updates when investigations change. The UI falls back to five-second polling when the stream is unavailable. Keep the API behind HTTPS in a deployed environment.
